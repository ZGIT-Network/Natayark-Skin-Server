# 从 Blessing Skin 迁移

这份说明面向已经运行 Blessing Skin、希望保留用户和材质的站点。新建站点请按 [README](../README.md) 安装。

Natayark Skin Server 是独立实现的程序，不能直接运行原站 PHP 插件。原站插件提供的功能是否已内置，请先看[兼容范围](compatibility.md)。当前原库验收基于一个安装了 OAuth、Yggdrasil 等插件的 Blessing Skin 站点及 MySQL 5.7.26；其他版本、定制字段和插件组合应先演练。

## 1. 备份原站

至少保存以下内容，并确认备份可以恢复：

- 完整数据库，包括插件表，而不仅是用户表。
- 原材质目录。默认是 `storage/textures`，设置过 `TEXTURES_DIR` 的站点以实际目录为准。
- 原 `.env` 中的密码算法、盐、数据库、SMTP 和第三方登录配置。
- 原 OAuth 签名密钥文件（若存在，例如 `storage/oauth-private.key`、`storage/oauth-public.key`），以及提供方登记的回调地址。

配置、密钥和数据库导出应保存在仓库外。

## 2. 在独立环境演练

准备独立数据库，导入原库的完整副本，并复制材质目录。不要让新旧程序同时写同一套生产表。在新程序目录执行：

```sh
npm ci
npm run setup
```

填写新 `.env`，重点核对：

| 配置 | 迁移时的处理 |
| --- | --- |
| `DB_*`、`DB_TABLE_PREFIX` | 指向演练库，前缀与导入后的表名一致。不能只改前缀而不复制对应表。 |
| `PWD_METHOD`、`SALT` | 保留原值；算法或盐不一致会使原密码无法验证。 |
| `TEXTURE_DIR` | 指向复制后的材质目录，保留哈希文件名。注意新配置为单数，原站可用的是 `TEXTURES_DIR`。 |
| `STORAGE_DIR` | 使用持久化目录；需要保留原 OAuth 签名身份时，将原签名密钥复制到此目录。 |
| `NYKID_KEY`、`NYKID_SECRET`、`LIVE_KEY`、`LIVE_SECRET` | 保留已使用的第三方登录客户端凭据，登记演练域名的回调。 |
| `MICROSOFT_KEY`、`MICROSOFT_SECRET` | Minecraft Java 正版验证应用凭据，与 Microsoft 网站登录分开；回调为 `PUBLIC_ORIGIN/mojang/callback`。 |
| `MAIL_*` | 保留可用的 SMTP。旧 `MAIL_ENCRYPTION=ssl` 通常对应 `MAIL_SECURE=true`，STARTTLS 通常用 `false`，以邮件服务要求为准。 |
| `PUBLIC_ORIGIN` | 新环境的完整外部地址，包含实际协议，不填反向代理内部地址。 |
| `APP_KEY` | 使用新程序生成的随机密钥；多个实例必须一致，部署后保持稳定。 |

对已有数据库运行迁移，再构建和启动：

```sh
npm run migrate -- --apply
npm run build
npm run dev
```

`migrate` 会检查基础站点表，补齐未安装相关插件时缺失的兼容表，并添加本项目扩展表。已有表的数据、字段和框架迁移历史不会被覆盖。库或前缀不对、缺少基础表时会拒绝执行；重复运行不会重建已有表。

**不要对已有站点运行 `db:init`，也不要用 `schema.sql` 覆盖原库。** 本项目直接读取兼容表，保留原 UID、角色、已有 UUID、材质 TID、衣柜和积分，不需要用户重新注册。

描述列仍是 `VARCHAR(255)` 时，程序按实际容量限制输入。如果需要更长描述，再显式扩容：

```sh
npm run migrate -- --apply --long-descriptions
```

MySQL DDL 不能完整事务回滚。迁移中途报错时保留日志，修复原因后重跑；不要删除原表尝试“重新初始化”。

## 3. 验证原账户与第三方登录

原网站的浏览器 cookie 不沿用，用户需要重新登录。原密码按保留的算法和盐验证，不会统一重置。

对于只按邮箱识别、未保存稳定第三方用户标识的旧账户，首次回调会要求验证一次原邮箱或原密码，再绑定到原 UID。原角色、UUID、材质和积分保留。没有本地密码的账户需要可用的原邮箱，因此切换前应确认 SMTP 能正常投递。

在提供方登记完整回调地址：

```text
https://你的域名/auth/login/natayarkid/callback
https://你的域名/auth/login/live/callback
```

演练时保留正式回调，不要提前把线上用户的回调替换到测试站。旧的进行中授权和无法恢复绑定的 refresh token 需要重新授权；保留签名文件不表示所有旧会话都能继续有效。

## 4. 对照原站验收

至少使用真实账户与客户端完成以下检查：

- 密码账户登录、签到、积分、衣柜和材质权限；比对迁移前后的 UID 与数量。
- 一个旧第三方账户完成首次关联，再退出并重新登录，确认仍进入原账户。
- 角色名及已有 UUID 保持一致，原皮肤和披风可预览、下载、应用；头像跟随已应用的皮肤。
- 上传、改名、公开／私有切换、举报与管理员操作按原站配置工作。
- 实际启动器登录、加入服务器及客户端显示皮肤；使用 Yggdrasil Connect 时再测相应授权流程。
- 后台的站点名称、首页、配色、版权、备案和第三方客户端配置符合预期。

自动化协议检查只能作为辅助，不能代替真实启动器和游戏客户端验收。

## 5. 正式切换与回退

1. 确定维护时间，停止原站写入，重新备份并导出最终数据库。
2. 导入正式目标库，补齐停机前新增的材质，运行迁移并核对数量。
3. 设置正式域名、HTTPS、反向代理和回调白名单，再启动新服务。多实例共享数据库、`APP_KEY`、签名身份及材质存储。
4. 重做一次登录、角色换肤和启动器验收，再恢复用户访问。

保留旧程序、最终备份和原回调配置，直到切换稳定。需要回退时，先停止新程序，再恢复同一时间点的数据库、材质与原程序配置。上线后的新写入不会自动合并回旧备份，回退前应单独保留这部分数据。
